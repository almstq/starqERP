00

The proposal in one paragraph

The AI Studio revision becomes the StarqERP client. The proven Supabase core stays underneath and is generalised, not rebuilt. Three things change at the boundary and everything else follows from them: the tenant stops being a constant, the workflow stops being code, and identity stops being an allowlist. The Flutter console is parked frozen. Nothing is deleted. The merge runs in nine phases, each leaving the system buildable and testable, behind a rollback tag that must be created before phase one begins.

The one finding that shaped everything

The core was already multi-tenant. Every operational table carries organisation_id, and the foreign keys are composite — garage_jobs references contacts(organisation_id, id) — so a cross-tenant reference is structurally impossible, not merely policy-blocked. The revision's tenantId already existed in the database.

That is why this is a merge measured in weeks rather than a rebuild measured in months.

Tenant isolation — two layers, and the first is the strong one

Structural: composite foreign keys make a cross-tenant reference impossible; the database refuses the write regardless of policy. Policy: RLS as the second lock. The organisation is resolved from session authority and never from a request payload.

§G tests both layers, and expects the foreign key to fail first. If a cross-tenant write ever succeeds at the FK layer, a composite key has been dropped somewhere — a graver finding than a missing policy.

Membership model: person → membership(organisation, role, status) → membership_seats. One person, many organisations, a different role and different seats in each.

Accounting additions: none. DEC-051. journal_lines.account_code stays free text with no accounts table, deliberately, so Postgres cannot hold a second opinion about the chart. The ERP emits journal_proposals; Python remains the only thing that posts.

Audit: unchanged in shape, changed in origin. logAuditEvent stops being something the client calls and becomes something the server does inside the same transaction as the mutation. An audit trail the actor can choose not to write is not evidence.

D

Front-End Decision

The revision is the primary UI. All forty view and component files become the StarqERP web application: dashboard, customers, jobs, invoices, payments, inventory, purchasing, reports, audit, settings, onboarding, AI copilot.

What carries across rather than being thrown away

The design tokens and the industrial red discipline — red only on the active action, outline never fill. And, more valuable than the CSS, the refusal semantics the console proved with a real person clicking things. SERP-151 established that a lock banner must distinguish held, held but not acting, and held by another role — and must name the role, never the person. The new client inherits that as specification.

What the revision must learn

Seats. That refusals are routine and correct rather than exceptional. And that some actions are visible-but-refused rather than hidden — DEC-065's segregation pairs bite even when a person holds every seat.

The discipline the whole decision rests on — memo §35

ERPContext.tsx becomes an API client: it coordinates, it does not decide. Accounting postings, tenant isolation, permission enforcement, stock mutation, approvals, reconciliation, audit, numbering and tax logic all live behind the API.

Front-end state is not a security boundary and not an accounting boundary.

Flutter console: parked frozen. It returns as the shop-floor technician client once the web application is live — the founder's own sequence at DEC-066: desktop web app to set up the organisation, then users, then the app. App is last.

E

API and Contract Decision

The finding

COMMAND_SEATS is Record<CommandName, SeatCode[]> — a compile-time map whose keys are CALL, BOOKING, INTAKE, ESTIMATE, AUTHORISATION, JOB_CARD, PARTS_PROCUREMENT, WORK, QC, HANDOVER, INVOICE_PAYMENT, CLOSE.

Those are one tenant's twelve workflow steps compiled into the authorization contract. A second tenant with different stages cannot be expressed in it at all.

Meanwhile Antigravity's inventory of ERPContext.tsx found twenty-five mutations, and the majority — create a customer, raise an invoice, receive stock, invite a user, authorise a user, create a role, create a tenant, add a workflow stage — have no command in the contract at all. The contract covers a garage's job journey and almost nothing a business does around it.

The decision: the contract splits into two layers

LayerExamplesAuthorizationLives as
Stage transitions The twelve steps — and whatever any other tenant defines workflow_stages.allowed_seats Data per tenant
Platform commands CUSTOMER_CREATE, INVOICE_ISSUE, PAYMENT_RECORD, STOCK_RECEIVE, STOCK_ADJUST, PURCHASE_*, USER_INVITE, USER_AUTHORIZE, USER_SUSPEND, ROLE_*, WORKFLOW_*, ORG_* Compile-time seat map — unchanged Constants tenant-independent

PURCHASE with its six SCM_STEPS and its segregation pairs is a platform command, not a workflow stage, and keeps its matrix exactly as it is. Procurement segregation is universal; paint booth stages are not.

Consequence to plan for, not discover

authorize() currently takes a CommandName. Splitting the layers changes that signature — and the seat vocabulary migration must precede the matrix change. The contract already warns that reversing the order “would convert a silent authorization hole into a hard outage.”

Contract version → 0.2.0. It reaches 1.0.0 on its own stated terms: every conformance test passing against a real runtime, and at least two of three runtimes importing their authorization decision from the file rather than reimplementing it.

On the demo tenant — where a quiet disaster would otherwise live

The revision carries sample TINs, bank account numbers, phone numbers, emails, supplier identities and invoice numbers. Memo §32 is right that they must be distinguishable from production, and the mechanism is stronger than a naming convention: the demo data lives in its own organisation, which the composite foreign keys then make structurally incapable of touching a real tenant's rows.

Demo separation becomes a property the database enforces rather than a discipline people remember.

Reseeded to a coherent August 2026 period — the revision's records sit in May 2025 and the interface looks stale the moment it opens — with dates internally consistent across invoices, payments, purchase orders, dashboards and GST periods. Metrics that cannot derive from events are removed rather than fabricated: 98.4% First Pass is hardcoded at ReportsView.tsx:261 and shows the same value against every technician.

mockData.ts is deleted after the wiring proves out, not before.

Restore test performed

The tag was cloned to a scratch tree and verified: 335 files, 11 migrations, contract present, Edge boundary present, Python engine present, 22 Dart files. git fsck clean.

What the restore test found — and it sharpens A1 rather than contradicting it

The tag does not cover the books. journals/ and books.db are gitignored — deliberately and correctly, because they are Tier 1 ledger data and the repository may go to GitHub. But the consequence is that the live journals sit in no repository at all: three files, protected only by backups/ on the same drive as the thing they protect against.

So SERP-173 covers three things, not one: the Supabase database, the repository including this tag, and the plain-text journals that are the books.

What remains open

Amendment A1 — SERP-173, a hard gate. An encrypted backup held independently of the development machine, a documented restoration procedure, and a passed restore test against that backup.

Gate Migration 0013 must not touch a live row until SERP-173 closes. DEC-019 closes with it.

Every subsequent phase branches, and 0013 is additionally rehearsed against a restored copy before it runs for real.

The eight amendments

Conditions of approval, not suggestions. Each is recorded against the phase it binds. Two of them can stop work rather than merely guide it.

#AmendmentWhere it lands
A1 Offsite backup is a hard gate. Encrypted, off-machine, documented restore procedure, and a passed restore test — before migration 0013 touches a live row. A tag on the development machine is not protection. Gate new SERP-173, blocks SERP-162
A2 One source of financial truth. Any statutory figure StarqERP shows must originate from, or reconcile to, the accounting engine. Operational analytics may compute independently; the client must not become a parallel accounting engine by accident. new SERP-174 — the invariant goes in the contract, with a conformance test
A3 Revalidate payment and expense mapping before the endpoints exist. Multiple payments per invoice, partial and unallocated payments, refunds, direct cash and card expense, petty cash, bank charges, bills paid later. new SERP-175, blocks SERP-167
A4 Currency is not structurally limited to MVR and USD. Base currency and transaction currency, ISO and extensible. No FX engine required; the door stays open. Already true in the schema — recorded as a guard on SERP-165, SERP-166
A5 Database identity and document number are separate concepts. Human references server-generated, organisation-aware, concurrency-safe, idempotency-compatible — with an acceptance test, not an implied responsibility. new SERP-176
A6 AI and storage stay feature-flagged off production data until the phase 8 isolation suite passes. Isolation is proven before exposure, not after. Gate SERP-172 now gates SERP-168
A7 Seed data uses the real entity model. Organisation Club Ignition Pvt Ltd, business name Ignition Ink. “Ignition Ink Garage Pvt Ltd” is retired — not as a spelling fix, but to prove the statutory entity is genuinely separated from the operating brand. SERP-162 seed, SERP-171 demo
A8 Roles-versus-seats precedence, written and tested. A role may make an action visible or generally available, but a protected action executes only when the seat and segregation contract also permits it. SERP-163 — contract text plus conformance test

The line A8 draws, in one sentence

A role cannot override a segregation-of-duties refusal. The test that proves it is adversarial: build a role granting every module and every action, hold it, and confirm a segregation pair still refuses. If it does not, roles have quietly become the authorization layer and the seat model is decoration.

Risks we are choosing to accept

  1. A core built with no live user drifts. Named at DEC-066 and unchanged. Mitigation unchanged too: the garage keeps running on paper and on the Python portal, and the paper is the specification, so tenant setup models what Ignition Ink actually does.
  2. Migration 0013 touches live jobs. The only phase that can lose data. Reversible, rehearsed, tagged.
  3. The contract split changes authorize(). Vocabulary before matrix, or a silent authorization hole becomes a hard outage.
  4. Two frontends were parked to avoid paying twice — and the console is where the refusal semantics were actually learned. The mitigation is that those semantics move into the new client as specification, not that the console stays alive.
