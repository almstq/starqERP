Executive Verdict: NOT READY

   starqERP presents as a polished ERP shell but is fundamentally a client-side simulation with no backend, no data
   persistence, and no tenant isolation. The product has critical architectural gaps that make it commercially unusable
   for any real business operations. While the UI is visually refined and the Material 3 design system is
   well-implemented, the underlying data layer is entirely fabricated.

   ---

   Critical Findings (Launch Blockers)

   1. No Backend Exists — Entire ERP is Client-Side Simulation

   Evidence: apiGateway.ts:40-51 is an in-memory client-side dispatcher. Zero fetch(), XMLHttpRequest, supabase, or
   WebSocket calls in web/src. contracts/commands.ts:1-36 states "Three runtimes must agree... They currently do not."
   Impact: Product advertised as ERP for Maldives SMEs has no server, no database, no API. All "business data" is
   fabricated mock data. No multi-user support, no real transactions, no real audit trail.
   Fix: Either (a) clearly label as demo/prototype and remove from commercial consideration, or (b) implement real
   backend with Supabase/PostgreSQL as contracts/commands.ts envisions.

   2. All Domain Data Lost on Browser Refresh

   Evidence: ERPContext.tsx:247-258 — customers, jobs, invoices, payments, expenses, inventory, stockMovements,
   suppliers, purchaseOrders, alerts, aiInsights, staff are all useState seeded from mockData.ts with no persistence.
   Only tenants array (lines 213-232) persists to localStorage key starq_erp_tenants_v1.
   Impact: User creates customers, invoices, payments, jobs, inventory items, purchase orders, expenses — all vanish on
   refresh. Only organization tenant config survives. This is complete data loss for all business operations.
   Fix: Implement backend persistence or at minimum localStorage persistence for all domain entities. Each CRUD action
   must persist to survive refresh.

   3. Document Numbering Produces Duplicates After Refresh

   Evidence: ERPContext.tsx:1085 (jobs: jobs.length + 240), 1119 (invoices: invoices.length + 88), 1220 (payments:
   payments.length + 1093), 1398 (expenses: expenses.length + 55), 1542 (POs: purchaseOrders.length + 43). Arrays reset
   to seeded counts on refresh, so numbering resets.
   Impact: User creates invoice INV-2026-093, refreshes browser, creates another invoice — gets INV-2026-093 again.
   Duplicate invoice numbers, payment references, expense IDs, PO numbers. Financial records become ambiguous and
   unreliable.
   Fix: Replace array.length-based numbering with monotonically increasing counters persisted to localStorage or
   backend.

   4. Zero Data Isolation Between Tenants

   Evidence: ERPContext.tsx:247-258 seeds one global array per entity from INITIAL_* mock data. types/erp.ts has NO
   tenantId field on Invoice, Payment, JobOrder, Expense, InventoryItem, Supplier, or PurchaseOrder. No component
   filters by tenant: grep across web/src/components shows tenantId appears in ZERO component files.
   Impact: When switching from Starq Tech to Club Ignition, the user sees the EXACT same customers, jobs, invoices,
   payments, expenses, inventory, suppliers. Only the header branding and currency symbol change. This is the core
   multi-tenant claim and it is entirely non-functional.
   Fix: Add tenantId to every domain entity type, stamp it in every creator function, and filter every list/stat/report
   computation by currentTenant.id before rendering.

   5. No Tenant Switcher UI Exists in Production Code

   Evidence: Grep for switchTenant across all src files shows it is ONLY called in test files. No component in
   src/components or src/app calls switchTenant. The AppShell header (AppShell.tsx:379-420) shows the current tenant
   name/logo as a button that navigates to /settings, but provides no dropdown or selector to switch tenants.
   Impact: Users cannot switch between tenants through the UI. The multi-tenant feature is inaccessible except through
   test harnesses.
   Fix: Add a tenant selector dropdown in the AppShell header. Populate it from the tenants array and call switchTenant
   on selection.

   6. Dashboard "New Work Order" and "New Invoice" Buttons Silently Do Nothing

   Evidence: DashboardView.tsx:187-198 — onClick={() => setIsCreateJobOpen(true)} and onClick={() =>
   setIsCreateInvoiceOpen(true)}. But DashboardView does NOT render <CreateJobModal /> or <CreateInvoiceModal />. These
   modals are only rendered inside JobsView.tsx:396 and InvoicesView.tsx:277 respectively.
   Impact: A user on the dashboard (the first page they see) clicks "New Work Order" or "New Invoice" and nothing
   happens. No modal appears, no error, no feedback. The primary call-to-action buttons on the landing page are broken.
   Fix: Either (a) import and render CreateJobModal, CreateInvoiceModal, and RecordPaymentModal inside AppShell.tsx so
   they are globally available, or (b) change the dashboard buttons to navigate('/jobs') and navigate('/invoices')
   instead.

   7. No Login Screen — App Opens Directly as Super Admin

   Evidence: main.tsx:9-17 renders <ThemeProvider><ERPProvider><RouterProvider /></ERPProvider></ThemeProvider> with no
   auth gate. ERPContext.tsx:240 — currentUserId defaults to 'user-1' (Ali Musthaq, Super Admin). There is no login
   route, no auth check, no redirect to a login page.
   Impact: Anyone who opens the URL has full unrestricted access to all data, all settings, all user management. There
   is no authentication barrier whatsoever.
   Fix: Implement an auth gate in main.tsx or a protected route wrapper that checks for an authenticated session before
   rendering the app.

   8. No Logout Button Exists Anywhere

   Evidence: Grep for logout|logOut|signout|signOut across all source files found matches only in test files. No
   component in the application renders a logout/sign-out button.
   Impact: Once logged in (automatically as Super Admin), there is no way to log out. The only option is to close the
   browser tab.
   Fix: Add a logout button to the user menu/workspace button in the AppShell header.

   9. Header Search Bar is a Dead Input — GlobalSearchModal Never Mounted

   Evidence: AppShell.tsx:339-358 — The search <input> has no onClick, onFocus, or onKeyDown handler. It is a plain
   <input type='search'> with placeholder='Search...' that does absolutely nothing when typed into or clicked.
   GlobalSearchModal.tsx exists as a component file but is never imported or rendered anywhere in the application.
   Impact: Users see a search bar in the top header of every page and expect it to search. Typing into it does nothing.
   The global search feature advertised in the aria-label is completely non-functional.
   Fix: Import and render <GlobalSearchModal /> inside AppShell, and wire the header search input's onFocus or onClick
   to call setIsGlobalSearchOpen(true).

   10. StarqAICopilot Never Mounted — Dashboard "starqAI" Button Opens Nothing

   Evidence: DashboardView.tsx:203 — onClick={() => setIsAICopilotOpen(true)}. However, grep confirms no file in the
   application contains import.*StarqAICopilot or <StarqAICopilot. The component file exists at
   components/ai/StarqAICopilot.tsx but is never rendered.
   Impact: The dashboard prominently features a "starqAI" button and "Open Copilot" link. Clicking them sets React state
    but nothing appears on screen. The AI copilot is advertised but invisible.
   Fix: Import and render <StarqAICopilot /> inside AppShell.tsx.

   11. Create Invoice Form Hardcodes GST to Zero

   Evidence: CreateInvoiceModal.tsx:83-85 — const gstRate = 0; const gstAmount = 0; const totalAmount = subtotal; —
   These are hardcoded constants, not derived from currentTenant.gstStatus or currentTenant.gstRate.
   Impact: A GST-registered business using this ERP would issue non-compliant tax invoices with zero GST to every
   customer. This is both a regulatory risk (MIRA non-compliance) and a revenue leak.
   Fix: Read currentTenant.gstStatus and currentTenant.gstRate in CreateInvoiceModal. When registered, compute gstAmount
    = Math.round(subtotal * (gstRate/100) * 100) / 100 and totalAmount = subtotal + gstAmount.

   12. Dashboard "Sales Today" KPI is Permanently Zero

   Evidence: ERPContext.tsx:331-336 — const today = new Date().toISOString().split('T')[0]; return invoices.filter((inv)
    => inv.date === today).reduce(...). All mock invoice dates are hardcoded to July-August 2026. Since the runtime date
    will never match these stale dates, totalSalesToday is always 0.
   Impact: The primary financial KPI on the operations dashboard always shows zero. A business owner opening the app
   every day will see "Sales Today: Rf 0" and "0 invoices logged" regardless of actual activity. This destroys trust in
   the dashboard.
   Fix: Either (a) change the label to "Total Invoiced (All Time)" and remove the date filter, or (b) seed mock data
   with today's date dynamically, or (c) add a date-range selector so the user can pick a meaningful period.

   13. Stock Movement History is Completely Invisible to Users

   Evidence: ERPContext.tsx:253 declares stockMovements state; lines 1034-1046, 1314-1331, 1438-1450, 1471-1483,
   1517-1529 create movement records. Grep for stockMovements across all components returns zero hits outside
   ERPContext.tsx.
   Impact: A garage owner can never audit what was received, deducted, adjusted, or wasted. Stock figures change but
   there is no movement ledger to reconcile against physical counts. This defeats the core purpose of inventory tracking
    in an ERP.
   Fix: Add a StockMovements table/view to InventoryView or as a sub-tab, consuming the stockMovements array from
   context.

   14. Counter-Sale (recordCounterSale) Has No UI Entry Point — Feature is Dead Code

   Evidence: ERPContext.tsx:1273-1395 defines recordCounterSale with full logic. Grep for recordCounterSale in
   components/ returns zero hits. Grep for CounterSale|counter sale in components/ returns zero hits.
   Impact: A garage selling spare parts or consumables over the counter has no way to record the sale. The entire POS
   workflow (stock deduction + invoice + payment in one step) is implemented but inaccessible.
   Fix: Build a Counter Sale modal/view accessible from the Inventory or Dashboard, invoking recordCounterSale with
   selected items.

   15. Logo Not Rendered in Invoice Print Output

   Evidence: InvoiceDetailView.tsx has no logo rendering code. Grep for logo|Logo in InvoiceDetailView.tsx returned no
   matches. Logo is only shown in AppShell header (AppShell.tsx:390-418) but not in commercial documents.
   Impact: Users upload custom logos expecting them to appear on customer-facing invoices and quotations, but logos only
    appear in the app header. This breaks brand consistency in commercial documents.
   Fix: Add tenant logo rendering to InvoiceDetailView header section (around line 50-95) similar to AppShell
   implementation.

   16. RBAC Configuration Lost on Refresh — False Persistence

   Evidence: ERPContext.tsx:238-243 — users, roles, workflowStages are React useState with no localStorage persistence.
   Only tenants array persists (lines 213-232). RolesPermissionsTab shows "Permissions Saved" toast (line 236-239) but
   data is lost on refresh.
   Impact: Administrators configure custom roles, assign permissions, invite users, and customize workflow stages, then
   refresh the page to find ALL configuration lost. This would cause severe frustration and data loss in production use.
   Fix: Persist roles, users, workflowStages to localStorage similar to tenants implementation.

   17. Seeded Job-Invoice Foreign Keys Point to Non-Existent Entities

   Evidence: mockData.ts:452 — job-1 linkedInvoiceId: 'inv-084'. The actual invoice for this job has id 'inv-2'
   (invoiceNumber 'INV-2026-084') at line 724. JobDetailView:537 renders <Link to={/invoices/${job.linkedInvoiceId}}>
   which navigates to /invoices/inv-084 — a route that resolves to no invoice, showing the "Invoice Not Found" error
   page.
   Impact: User clicks the invoice link on the most prominent seeded job (Ahmed Rauf's Prado) and lands on an error
   page. The core "inspect linked document" workflow is broken for the first thing a demo user sees.
   Fix: Change linkedInvoiceId: 'inv-084' to linkedInvoiceId: 'inv-2' in mockData.ts line 452.

   18. Seeded Customer Financial Metrics Contradict Actual Seeded Invoices

   Evidence: cust-1 (Ahmed Rauf): totalInvoiced: 85000 (mockData.ts:43) but the only invoice for cust-1 is inv-2 with
   totalAmount: 48500. cust-4 (TMA Fleet): totalInvoiced: 142000 (mockData.ts:123) but inv-1 totalAmount is 42700.
   Impact: The customer list and detail view show "Total Invoiced" and "Outstanding Balance" figures that are materially
    wrong vs. the invoices the same user can inspect. A business owner would immediately lose trust in the system's
   numbers.
   Fix: Either compute initial customer.totalInvoiced and outstandingBalance from the seeded invoices/payments at
   startup, or adjust the seeded values to match the actual seeded invoice/payment data.

   19. Inventory Category Filter is Broken for 4 of 5 Non-All Options

   Evidence: InventoryView.tsx:298-303 filter options: "Clearcoats & Hardeners", "Vinyl & PPF Film", "Detailing &
   Ceramics", "Abrasives & Sandpaper". Mock data categories: "Clearcoats & Hardener", "Vinyl & PPF Wraps", "Compounds &
   Detailing", "Abrasives & Sanding". Only "Paints & Primers" matches.
   Impact: Selecting any category filter other than "Paints & Primers" shows zero results, making it appear that the
   garage has no stock in those categories.
   Fix: Align filter option values with actual category strings from the data, or derive filter options dynamically from
    the unique categories in the inventory array.

   20. receivePurchaseOrder Marks PO as Paid Without Reducing Supplier outstandingPayable

   Evidence: ERPContext.tsx:1577-1578 sets paymentStatus: 'Paid' on receive. createPurchaseOrder (line 1552-1558) adds
   to outstandingPayable. receivePurchaseOrder (lines 1572-1594) never subtracts from outstandingPayable.
   Impact: After receiving and "paying" for a PO, the supplier's Accounts Payable total never decreases. The Total
   Accounts Payable KPI on PurchasingView (line 73) will permanently inflate with every PO received, making the figure
   meaningless.
   Fix: Either: (a) separate receiving from payment — don't set paymentStatus to "Paid" on receive, and add a separate
   "Record Supplier Payment" action that reduces outstandingPayable; or (b) on receive, reduce
   supplier.outstandingPayable by po.totalAmount.

   High Findings (Not Launch Blockers but Serious)

   21. Audit Logs Hardcode Fake IP Address and Location

   Evidence: ERPContext.tsx:377 — ipAddress: '123.231.104.18 (Dhiraagu Maldives)' hardcoded in logAuditEvent. Line 378:
   location: \${currentTenant.island} Office`. Seeded INITIAL_AUDIT_LOGScontain fabricated audit entries with fake IPs,
   timestamps, user actions.   **Impact**: Audit trail shows fake IP addresses for all actions. Seeded audit history
   presents fabricated events as real. Audit log is legally worthless for compliance or dispute resolution.   **Fix**:
   Remove hardcoded IP. Either implement real IP detection (requires backend) or omit IP field entirely. Remove
   seededINITIAL_AUDIT_LOGS` or clearly label as sample data.

   22. MFA is Simulated, Not Real

   Evidence: MfaSetupModal.tsx:21 — secret hardcoded as 'JBSWY3DPEHPK3PXP'. Line 252: "Tip: In simulation mode, code
   123456 is valid". ERPContext.tsx:533,606 — verifyMfaChallenge accepts any 6-digit code except '000001' and '999998'.
   No real TOTP validation.
   Impact: MFA provides zero security. Any 6-digit code works. MFA state lost on refresh. Users may believe their admin
   account is protected when it is not.
   Fix: Implement real TOTP validation using a library like otplib. Store MFA secrets encrypted in backend. Persist MFA
   enrollment state. Or remove MFA UI until real implementation exists.

   23. Users, Roles, Workflow Config Lost on Refresh

   Evidence: ERPContext.tsx:238-243 — users, roles, workflowStages are useState seeded from INITIAL_USERS,
   INITIAL_ROLES, INITIAL_WORKFLOW_STAGES with no persistence. inviteUser (739-789), createRole (815-833),
   addWorkflowStage (867-887) all modify React state only.
   Impact: Admin invites users, creates custom roles, configures workflow stages — all vanish on refresh. User
   management and workflow configuration are non-functional for production use.
   Fix: Persist users, roles, workflowStages to localStorage or backend.

   24. recordPayment Does Not Update Linked Job Status to Paid/Completed

   Evidence: ERPContext.tsx:1219-1271 — recordPayment updates invoices (lines 1230-1245) and customers (lines 1248-1259)
    but never touches the jobs array. When an invoice is fully paid (balanceDue reaches 0), the linked job remains in
   whatever status it was.
   Impact: After fully paying an invoice, the user navigates to the job and it still shows "In Progress" or "Invoiced" —
    not "Paid" or "Settled". The kanban board continues showing the job as active.
   Fix: In recordPayment, after updating the invoice, find the linked job (via invoice.linkedJobId) and if invoice
   balance is now 0, set job status to "Paid" or "Tax Invoiced & Settled".

   25. Overpayment Silently Accepted; amountPaid Can Exceed totalAmount

   Evidence: RecordPaymentModal.tsx:146 — max={selectedInvoice?.balanceDue || undefined} — HTML max attribute is a UI
   hint only, not enforced. ERPContext.tsx:1233 — newPaid = inv.amountPaid + paymentData.amount with no cap. Line 1234:
   newBalance = Math.max(0, inv.totalAmount - newPaid) clamps balance to 0 but amountPaid is unbounded.
   Impact: A user typing MVR 50,000 instead of 5,000 records a 50k payment against a 18,500 balance. The invoice shows
   amountPaid: 80,000 on a 30,000 invoice. Financial reports would be materially wrong.
   Fix: In recordPayment, validate paymentData.amount <= invoice.balanceDue and reject or warn. Cap amountPaid at
   totalAmount.

   26. Invoice Detail Hardcodes "Non-GST Registered" Regardless of Actual Tax Data

   Evidence: InvoiceDetailView.tsx:169-170 — <span className='erp-muted'>Tax Status:</span><span className='font-mono
   erp-muted'>Non-GST Registered</span>. This is static text. Yet seeded invoices inv-2 through inv-5 all have gstRate:
   0.08 and gstAmount > 0.
   Impact: Every invoice with GST shows "Non-GST Registered" in the totals section. For a Maldives ERP advertising MIRA
   GST compliance, this is a direct contradiction that would concern accountants.
   Fix: Conditionally render based on invoice.gstRate > 0 — show "GST Registered (8%)" when tax is present.

   27. PaymentsView Bank Account Balances Are Hardcoded Static Theater

   Evidence: PaymentsView.tsx:187,202,217 — "MVR 342,890.00", "MVR 88,400.00", "MVR 12,500.00". These are literal
   strings, not computed from payments, invoices, or any state. They never change regardless of recorded payments.
   Impact: The prominent "Account Balances Strip" at the top of the Payments page shows numbers that are completely
   disconnected from reality. After recording a payment, the balances don't update. This is display-only theater that
   misleads the user about actual cash position.
   Fix: Either compute running balances from payment data (segmented by bankAccount field) or label these clearly as
   "Opening Balances" / static reference values.

   28. All Charts (Dashboard + Reports) Use Static Hardcoded Data

   Evidence: mockData.ts:1251-1258 — MONTHLY_SALES_CHART_DATA is a static array of 6 objects. Both DashboardView.tsx:554
    and ReportsView.tsx:410 import and render this static array directly. The charts never reflect actual invoices,
   payments, or expenses in state.
   Impact: The "Financial Performance" chart on the dashboard and "Monthly Financial Overview" on the reports page show
   fabricated numbers that have no relationship to the actual invoice/payment/expense data.
   Fix: Compute monthly revenue/expenses/profit from actual invoices, payments, and expenses state, grouped by month. Or
    clearly label charts as "Sample Data".

   29. Supplier outstandingPayable Values Are Inconsistent with Purchase Order Totals

   Evidence: mockData.ts — sup-1 outstandingPayable=14,250 but PO-2026-041 for sup-1 has totalAmount=15,444 (status
   Sent, Unpaid). sup-2 outstandingPayable=22,800 but PO-2026-042 for sup-2 has totalAmount=26,568 (status Sent,
   Partially Paid). sup-3 outstandingPayable=8,350 but has no POs in the system.
   Impact: The dashboard "Accounts Payable" KPI shows Rf 52,400 (from supplier records) while the Reports Trial Balance
   shows Accounts Payable as Rf 42,012 (from PO computation). A business owner sees two different payable figures on two
    screens of the same app, undermining confidence in both.
   Fix: Either compute supplier.outstandingPayable dynamically from their unpaid/partially-paid POs, or have
   totalAccountsPayable use the bookkeeping engine's figure.

   30. No Focus Trap in Any Modal or Drawer Component

   Evidence: ui/Modal.tsx:24-32 (Escape handler only, no focus trap); ui/Drawer.tsx:25-31 (same); common/Modal.tsx:23-35
    (same); GlobalSearchModal.tsx:33-43 (same); AppShell.tsx:241-312 (mobile drawer - no Escape handler at all, no focus
    trap). Searched entire src/ for focus-trap|focusTrap|trapFocus — zero matches.
   Impact: When a screen-reader or keyboard user opens any modal/drawer, Tab will move focus into background page
   content behind the scrim. This is a WCAG 2.1.2 failure.
   Fix: Implement a focus-trap hook (e.g., trap focus within the dialog on Tab/Shift-Tab, return focus to trigger on
   close).

   31. All Primary Button Sizes Are Below 44px Minimum Touch Target

   Evidence: Button.tsx:27 — xs = h-7 (28px); line 28: sm = h-8 (32px); line 29: md = h-9 min-h-[36px] (36px); line 30:
   lg = h-11 min-h-[44px] (44px, only this passes). DashboardView uses size='sm' for all primary actions (lines
   185-207).
   Impact: On a 375px phone, the most commonly used buttons (sm, md) are 28-36px tall — below the WCAG 2.5.5 target size
    of 44px and the M3 minimum of 48px. Users will experience frequent mis-taps.
   Fix: Set minimum touch target to min-h-[44px] for all interactive controls on compact viewports.

   32. GlobalSearchModal Claims Arrow-Key Navigation But Implements None

   Evidence: GlobalSearchModal.tsx:290 — <span>Navigate with mouse or arrow keys</span> but the file contains no
   onKeyDown handler for ArrowUp/ArrowDown. Search results are <div onClick> elements with no tabIndex, no
   role='option', and no active-descendant pattern.
   Impact: Keyboard users see the footer hint "Navigate with mouse or arrow keys" but arrow keys do nothing. They must
   use Tab to reach each result div, and since divs are not focusable by default, they cannot reach them at all without
   Tab cycling through the entire page.
   Fix: Either implement arrow-key navigation with aria-activedescendant on the input and role='option' on results, or
   remove the misleading footer text.

   Medium Findings

   33. Fake Business Data Presented as Real

   Evidence: mockData.ts:1143-1196 INITIAL_ALERTS (overdue invoices, low stock, supplier dues), 1198-1249
   INITIAL_AI_INSIGHTS (fabricated business intelligence), 1251-1265 MONTHLY_SALES_CHART_DATA (static revenue/expense
   charts), 16-22 INITIAL_STAFF (fake employee names). All seeded as if real.
   Impact: Dashboard shows fake alerts about overdue invoices that don't exist. AI insights recommend actions on

   fake data.
   Fix: Either (a) remove all seeded mock data and start with empty state, showing "No data yet" prompts, or (b) clearly
    label demo data with "DEMO" watermark or banner.

   34. Onboarding Creates Tenant But No Domain Data

   Evidence: OrganisationSetupModal.tsx:114-139 calls createTenant. ERPContext.tsx:400-442 createTenant adds to tenants
   array, applies workflow preset, sets user to Active. Does NOT create customers, inventory, invoices, or any domain
   entities.
   Impact: After completing onboarding, user sees empty dashboard (except for seeded mock data from default tenant). No
   guided data import, no sample data creation, no next-steps guidance. Onboarding feels incomplete.
   Fix: Add optional sample data creation during onboarding, or provide clear "Import your data" or "Start adding
   customers" next steps.

   35. Telemetry Never Sends Data Anywhere

   Evidence: telemetry.ts:83-146 — TelemetryService buffers events in memory array. track() method (90-137) validates
   and buffers but never transmits. getBufferedEvents() returns in-memory array. No fetch, no WebSocket, no backend
   call.
   Impact: Product analytics are non-functional. No usage data is collected. Privacy-preserving design is good, but
   implementation is incomplete. Product team has no visibility into usage patterns.
   Fix: Implement telemetry transmission to a backend endpoint, or remove telemetry code until backend exists.

   36. formatMVR Decimal Inconsistency

   Evidence: DashboardView.tsx:218,237,256,275 — formatMVR(value, false) — no decimals. InvoicesView.tsx:127 —
   formatMVR(inv.totalAmount) — with decimals. InvoicesView.tsx:142 — inv.balanceDue > 0 ? formatMVR(inv.balanceDue) :
   '0.00' — bare string without currency symbol.
   Impact: Minor visual inconsistency. The "0.00" without currency symbol breaks the pattern and looks like a bug.
   Fix: Replace hardcoded "0.00" with formatMVR(0). Consider standardizing on showDecimals=true everywhere.

   37. generateJobInvoice Does Not Round subtotal/gstAmount to 2 Decimal Places

   Evidence: ERPContext.tsx:1161-1163 — const subtotal = job.quotedAmount / (1 + gstRateDecimal); const gstAmount =
   job.quotedAmount - subtotal; — No Math.round. For quotedAmount=48500 and gstRate=0.08: subtotal=44907.40740740... and

   Impact: Auto-generated invoices from jobs will display amounts like "Rf 44,907.41" (Intl.NumberFormat rounds display)

   drift could cause pennies-off discrepancies in reports.

   used in recordCounterSale.

   39. Reports Date-Range Selector Has No Effect on Computed Financial Statements

   40. Logo Upload Lacks localStorage Quota Error Handling

   Top 10 Things Starq Should Fix Before the First Paying External Client

   1. Implement Real Backend Persistence

   Priority: CRITICAL — Launch Blocker
   Why: The entire ERP is a client-side simulation with no server, no database, no API. All "business data" is
   fabricated mock data. No multi-user support, no real transactions, no real audit trail. This is the single most
   critical blocker.
   Fix: Implement real backend with Supabase/PostgreSQL as contracts/commands.ts envisions. Connect the web client to
   the backend via apiGateway.ts. Remove all mock data seeding.

   2. Persist All Domain Data to Survive Browser Refresh

   Priority: CRITICAL — Launch Blocker
   Why: All domain data (customers, jobs, invoices, payments, expenses, inventory, stockMovements, suppliers,
   purchaseOrders, users, roles, workflowStages, auditLogs) is lost on browser refresh. Only tenant config survives.
   This is catastrophic data loss for any real usage.
   Fix: Persist all domain entities to localStorage (minimum) or backend (required for production). Each CRUD action
   must persist to survive refresh.

   3. Implement Tenant Data Isolation

   Priority: CRITICAL — Launch Blocker
   Why: Zero data isolation between tenants. All domain data is global. When switching tenants, the user sees the EXACT
   same customers, jobs, invoices, payments, expenses, inventory, suppliers. Only the header branding and currency
   symbol change. This is the core multi-tenant claim and it is entirely non-functional.
   Fix: Add tenantId to every domain entity type, stamp it in every creator function, and filter every list/stat/report
   computation by currentTenant.id before rendering.

   4. Add Tenant Switcher UI

   Priority: CRITICAL — Launch Blocker
   Why: No tenant switcher UI exists in production code. The switchTenant function is only called in test files. Users
   cannot switch between tenants through the UI. The multi-tenant feature is inaccessible except through test harnesses.
   Fix: Add a tenant selector dropdown in the AppShell header. Populate it from the tenants array and call switchTenant
   on selection.

   5. Fix Dashboard Primary Action Buttons

   Priority: CRITICAL — Launch Blocker
   Why: Dashboard "New Work Order" and "New Invoice" buttons silently do nothing. They set React state but the modals
   are not rendered on the Dashboard route. The primary call-to-action buttons on the landing page are broken.
   Fix: Either (a) import and render CreateJobModal, CreateInvoiceModal, and RecordPaymentModal inside AppShell.tsx so
   they are globally available, or (b) change the dashboard buttons to navigate('/jobs') and navigate('/invoices')
   instead.

   6. Implement Authentication (Login/Logout)

   Priority: CRITICAL — Launch Blocker
   Why: No login screen — app opens directly as Super Admin with no authentication. Anyone who opens the URL has full
   unrestricted access to all data, all settings, all user management. There is no authentication barrier whatsoever. No
    logout button exists anywhere.
   Fix: Implement an auth gate in main.tsx or a protected route wrapper that checks for an authenticated session before
   rendering the app. Add a logout button to the user menu/workspace button in the AppShell header.

   7. Wire Up Global Search and AI Copilot

   Priority: CRITICAL — Launch Blocker
   Why: Header search bar is a dead input — GlobalSearchModal is never mounted. StarqAICopilot is never mounted —
   dashboard "starqAI" button opens nothing. These are advertised features that don't exist.
   Fix: Import and render <GlobalSearchModal /> and <StarqAICopilot /> inside AppShell.tsx. Wire the header search
   input's onFocus or onClick to call setIsGlobalSearchOpen(true).

   8. Fix GST Tax Calculation in Invoice Creation

   Priority: CRITICAL — Launch Blocker
   Why: Create Invoice form hardcodes GST to zero. All manually created invoices are tax-free. A GST-registered business
    using this ERP would issue non-compliant tax invoices with zero GST to every customer. This is both a regulatory
   risk (MIRA non-compliance) and a revenue leak.
   Fix: Read currentTenant.gstStatus and currentTenant.gstRate in CreateInvoiceModal. When registered, compute gstAmount
    = Math.round(subtotal * (gstRate/100) * 100) / 100 and totalAmount = subtotal + gstAmount.

   9. Fix Dashboard "Sales Today" KPI

   Priority: CRITICAL — Launch Blocker
   Why: Dashboard "Sales Today" KPI is permanently zero. All mock invoice dates are hardcoded to July-August 2026. Since
    the runtime date will never match these stale dates, totalSalesToday is always 0. The primary financial KPI on the
   operations dashboard always shows zero. This destroys trust in the dashboard.
   Fix: Either (a) change the label to "Total Invoiced (All Time)" and remove the date filter, or (b) seed mock data
   with today's date dynamically, or (c) add a date-range selector so the user can pick a meaningful period.

   10. Add Stock Movement Visibility and Counter-Sale UI

   Priority: CRITICAL — Launch Blocker
   Why: Stock movement history is completely invisible to users. A garage owner can never audit what was received,
   deducted, adjusted, or wasted. Counter-sale (recordCounterSale) has no UI entry point — feature is dead code. A
   garage selling spare parts or consumables over the counter has no way to record the sale.
   Fix: Add a StockMovements table/view to InventoryView or as a sub-tab. Build a Counter Sale modal/view accessible
   from the Inventory or Dashboard, invoking recordCounterSale with selected items.

   Summary

   starqERP has a polished UI and a well-implemented Material 3 design system, but the underlying product is
   fundamentally a client-side simulation with no backend, no data persistence, and no tenant isolation. The product has
    20 critical launch blockers that must be fixed before any paying external client can use it. The top 10 fixes above
   represent the minimum viable product for commercial launch.

   Recommendation: Do not launch to any paying external client until all 20 critical findings are resolved. The product
   is currently suitable only for internal demo/prototype purposes.
